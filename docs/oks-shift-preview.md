# ОКС — дежурства и проверка смены

Администратор ведёт назначения в «Дежурные ОКС». Назначение содержит дату по Europe/Rome, ключ настроенного района и сотрудника. На район и дату допускается одно назначение. Один сотрудник может иметь назначения в нескольких районах. Выбор ограничен активными одобренными сотрудниками. Потребуется новая миграция основной базы `2026_11_15_000000_create_shift_duties_table.php` после обычной проверки и резервирования.

Районы берутся из существующего `services.telegram.digest_districts` через `TelegramDistrictRouteRegistry::sourceRoutes()`. Отсутствие темы отправки дежурства не препятствует локальному просмотру района. Некорректные маршруты перечислены в диагностике JSON. Автоматические назначения по автору сообщения, членству в чате или прошлой дате отсутствуют.

Проверка смены доступна командой:

```bash
php artisan telegram:shift-preview --date=2026-06-17
php artisan telegram:shift-preview --date=2026-06-17 --json
```

Просмотр объединяет назначения с существующими вечерними результатами по каждому району. Ledger ситуаций, подтверждённые ответы и решения, ссылки на источники, предварительное окно дня и качество входных данных формируются существующим `TelegramEveningIntelligenceBuilder`. Команда выполняет только чтение и ничего не отправляет. Статусы назначения `unassigned` и `unavailable` сохраняются явно.

## Проверенный сценарий

`tests/Feature/TelegramShiftPreviewTest.php` создаёт изолированную синтетическую схему, назначает одного супервайзера в два района, проводит сообщение о сломанном замке и ответ о ремонте через существующий observer, оставляет отдельную открытую ситуацию во втором районе и проверяет раздельные результаты команды. Дополнительно проверены создание через действие Filament, повторное назначение того же района, неактивный сотрудник, отсутствие назначения и запрет управления для супервайзера.

## Оставшаяся приёмка

Реальные назначения и реальные Telegram-сообщения в рамках разработки не использовались. Нужен разрешённый фактический прогон смены после настройки источников. Браузерный smoke-test административной формы ещё требуется.

Дежурный района указывается явно. Индивидуальный ответственный за конкретную ситуацию и отдельное ручное решение по ней сейчас в ledger не хранятся. Автор сообщения и автор подтверждения решения остаются авторами источников. Указание дежурного не назначает его исполнителем всех ситуаций. Если требуется отдельное назначение исполнителя ситуации, это следующий согласуемый шаг модели и интерфейса.

Демонстрационный HTML-виджет ОКС сохраняет маркировку демо. Новые назначения и сводка пока доступны в административном ресурсе и команде просмотра.
