# ОКС — дежурства и проверка смены

Рабочий бот открывает смену в теме утреннего контроля `schedule_checked`. Планировщик ищет единственную активную тему с таким контролем на текущий день. Время открытия по умолчанию 09:00 по Риму, его можно задать через `TELEGRAM_OKS_SHIFT_OPENING_TIME` в формате `HH:MM`. Открытие должно предшествовать утреннему контролю.

В Telegram-карточке администратор с привязанным аккаунтом выбирает для каждого района дежурного или «Нет уборок» и сохраняет назначения. Выбор ограничен активными одобренными сотрудниками с привязанным Telegram. Один сотрудник может дежурить в нескольких районах. Следующие контроли в этой теме используют сохранённый список районов и принимают ответ по району от его дежурного. Пока план не подтверждён, контроли следуют своим обычным правилам.

Для предпросмотра и ручного ведения дежурств есть административный ресурс «Дежурные ОКС». Назначение содержит дату по Риму, район и сотрудника. Потребуются миграции основной базы `2026_11_15_000000_create_shift_duties_table.php` и `2026_11_15_000001_create_shift_situations_table.php`.

Telegram-карточка использует районы утренних контролей. Для предпросмотра районы берутся из существующего `services.telegram.digest_districts` через `TelegramDistrictRouteRegistry::sourceRoutes()`. Некорректные маршруты перечислены в диагностике JSON.

Проверка смены доступна командой:

```bash
php artisan telegram:shift-preview --date=2026-06-17
php artisan telegram:shift-preview --date=2026-06-17 --json
php artisan telegram:shift-preview --date=2026-06-17 --opening --json
```

Просмотр объединяет назначения с существующими вечерними результатами по каждому району. Ledger ситуаций, подтверждённые ответы и решения, ссылки на источники, предварительное окно дня и качество входных данных формируются существующим `TelegramEveningIntelligenceBuilder`. Команда выполняет только чтение и ничего не отправляет. Статусы назначения `unassigned` и `unavailable` сохраняются явно.

`--opening` формирует предпросмотр сводки по имеющимся назначениям и открытым ситуациям с подтверждёнными источниками. С `--json` команда выдаёт Rich Markdown и обычный HTML. Интерактивную карточку с кнопками отправляет планировщик.

## Ответственный и решение по ситуации

В административном ресурсе «Ситуации ОКС» выбираются дата, район и существующая ситуация журнала, затем назначается активный одобренный сотрудник. Решение можно дописать позднее. Ситуация должна иметь действующее доказательство в выбранном районе в пределах календарного дня Europe/Rome. Подмена района, даты или ключа ситуации отклоняется на сервере. Уникальность даты, района и ключа обеспечивается также основной базой.

Назначение и текст решения хранятся в основной базе в `shift_situations` со стабильным `event_key` аналитического журнала. Между базами отсутствует внешний ключ. `recorded_by` фиксирует администратора последнего сохранения. Автора исходного сообщения и дежурного района система не подставляет исполнителем ситуации. Ручное решение сохраняет текст поручения, а подтверждённый результат ремонта продолжает поступать через существующий Telegram observer.

В JSON и текстовом предпросмотре видны ситуации, исполнители, принятые решения и статус журнала. При исчезновении актуального источника для выбранного дня сохранённая запись остаётся видна с `source_status=unavailable`. При увольнении исполнителя его имя остаётся в истории с `assignment_status=unavailable`. При отсутствии ручного назначения ситуация получает `assignment_status=unassigned`.

## Проверенный сценарий

`tests/Feature/TelegramShiftPreviewTest.php` создаёт изолированную синтетическую схему, назначает одного супервайзера в два района, проводит сообщение о сломанном замке и ответ о ремонте через существующий observer, оставляет отдельную открытую ситуацию во втором районе и проверяет раздельные результаты команды. Второй сценарий через реальные действия Filament назначает другого сотрудника исполнителем ситуации, сохраняет ручное решение, получает подтверждение ремонта через observer и проверяет результат в предпросмотре без изменения дежурного. Дополнительно проверены повторные назначения, подмена района/даты/ключа, неактивный исполнитель, отсутствие назначения, потеря источника и запрет управления для супервайзера.

## Оставшаяся приёмка

Реальные назначения и реальные Telegram-сообщения в рамках разработки не использовались. Нужен разрешённый фактический прогон смены после настройки источников. Браузерный smoke-test административной формы ещё требуется.

Локальный тест `TelegramScheduledMessagesTest` проверяет отправку через Bot API, сохранение назначений, состав следующего контроля и проверку дежурного при ответе. Telegram в тесте подменён.

## Актуальные контроли ОКС

`TELEGRAM_OKS_CURRENT_CONTROLS_ENABLED=true` переключает один рабочий топик на новый сценарий. Топик определяется по включённому контролю «Время уборок и заметки» в 09:30. Дни работы берутся из его расписания. Нужен `TELEGRAM_BOT_USERNAME` бота с настроенным Main Mini App. При нескольких подходящих топиках переключение не выполняется.

Открытие в 09:00. Администратор или супервайзер с привязанным Telegram нажимает «Есть» и становится дежурным или нажимает «Нет». Каждая отметка сохраняется сразу. Первый ответ закрепляет район, остальные дежурные могут продолжить отмечать свои районы. В контролях показываются районы с дежурными к моменту отправки. Районы без отметки видны в карточке открытия. При отсутствии подтверждённого открытия или активных районов новый контроль помечается пропущенным.

Время по Риму. 09:30 график и заметки, 10:15 старт уборок на 10:00 и поздние выезды, 11:00 старт уборок до 11:00 и освобождение квартир, 11:05 бельё в приоритетных квартирах, 12:00 ход первых уборок, 12:30 риск сдвига следующих, 14:00 готовность к заезду, 16:00 доставки, 17:30 завершение уборок, 18:00 доплаты. Контроль доплат идёт по расписанию.

В карточке дежурный подтверждает каждый вопрос отдельно. Кнопка с отрицательным ответом открывает форму с одним текстовым полем. Сохранение обновляет исходное сообщение и историю контроля. Если у шаблона 09:30 включено «Напоминать при отсутствии ответа», бот отправляет одно напоминание на контроль по всем ожидающим районам. EXTRA TIME и передача информации PM указаны как рабочие действия для дежурного.
