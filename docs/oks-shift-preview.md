# ОКС — дежурства и проверка смены

Администратор ведёт назначения в «Дежурные ОКС». Назначение содержит дату по Europe/Rome, ключ настроенного района и сотрудника. На район и дату допускается одно назначение. Один сотрудник может иметь назначения в нескольких районах. Выбор ограничен активными одобренными сотрудниками. Потребуются новые миграции основной базы `2026_11_15_000000_create_shift_duties_table.php` и `2026_11_15_000001_create_shift_situations_table.php` после обычной проверки и резервирования.

Районы берутся из существующего `services.telegram.digest_districts` через `TelegramDistrictRouteRegistry::sourceRoutes()`. Отсутствие темы отправки дежурства не препятствует локальному просмотру района. Некорректные маршруты перечислены в диагностике JSON. Автоматические назначения по автору сообщения, членству в чате или прошлой дате отсутствуют.

Проверка смены доступна командой:

```bash
php artisan telegram:shift-preview --date=2026-06-17
php artisan telegram:shift-preview --date=2026-06-17 --json
```

Просмотр объединяет назначения с существующими вечерними результатами по каждому району. Ledger ситуаций, подтверждённые ответы и решения, ссылки на источники, предварительное окно дня и качество входных данных формируются существующим `TelegramEveningIntelligenceBuilder`. Команда выполняет только чтение и ничего не отправляет. Статусы назначения `unassigned` и `unavailable` сохраняются явно.

## Ответственный и решение по ситуации

В административном ресурсе «Ситуации ОКС» выбираются дата, район и существующая ситуация журнала, затем назначается активный одобренный сотрудник. Решение можно дописать позднее. Ситуация должна иметь действующее доказательство в выбранном районе в пределах календарного дня Europe/Rome. Подмена района, даты или ключа ситуации отклоняется на сервере. Уникальность даты, района и ключа обеспечивается также основной базой.

Назначение и текст решения хранятся в основной базе в `shift_situations` со стабильным `event_key` аналитического журнала. Между базами отсутствует внешний ключ. `recorded_by` фиксирует администратора последнего сохранения. Автора исходного сообщения и дежурного района система не подставляет исполнителем ситуации. Ручное решение сохраняет текст поручения, а подтверждённый результат ремонта продолжает поступать через существующий Telegram observer.

В JSON и текстовом предпросмотре видны ситуации, исполнители, принятые решения и статус журнала. При исчезновении актуального источника для выбранного дня сохранённая запись остаётся видна с `source_status=unavailable`. При увольнении исполнителя его имя остаётся в истории с `assignment_status=unavailable`. При отсутствии ручного назначения ситуация получает `assignment_status=unassigned`.

## Проверенный сценарий

`tests/Feature/TelegramShiftPreviewTest.php` создаёт изолированную синтетическую схему, назначает одного супервайзера в два района, проводит сообщение о сломанном замке и ответ о ремонте через существующий observer, оставляет отдельную открытую ситуацию во втором районе и проверяет раздельные результаты команды. Второй сценарий через реальные действия Filament назначает другого сотрудника исполнителем ситуации, сохраняет ручное решение, получает подтверждение ремонта через observer и проверяет результат в предпросмотре без изменения дежурного. Дополнительно проверены повторные назначения, подмена района/даты/ключа, неактивный исполнитель, отсутствие назначения, потеря источника и запрет управления для супервайзера.

## Оставшаяся приёмка

Реальные назначения и реальные Telegram-сообщения в рамках разработки не использовались. Нужен разрешённый фактический прогон смены после настройки источников. Браузерный smoke-test административной формы ещё требуется.

Демонстрационный HTML-виджет ОКС сохраняет маркировку демо. Новые назначения и сводка пока доступны в административном ресурсе и команде просмотра.
